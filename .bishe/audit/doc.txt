[132][s2] 1  设计任务
[133][s34] 1.1 项目背景
[134][s35] 近年来，我国居民健康意识显著提升，可穿戴设备与家用检测仪器快速普及，个人健康数据的获取成本大幅下降。心率、血压、血糖、体重、睡眠等指标可以按天甚至按小时被连续采集，健康管理由此具备了从“事后就医”转向“事前预防”的数据基础。国务院《关于实施健康中国行动的意见》明确提出要“推动健康管理服务个性化、智能化”，以信息化手段提升居民自我健康管理能力，已成为公共卫生领域的重要方向。
[135][s35] 然而，个人健康数据的管理现状并不理想，主要存在四个方面的问题。其一，数据分散。手环记录的睡眠、体检报告里的化验值、家中血压计的历史读数分别存放在不同平台，用户难以获得完整的健康视图。其二，指标解读门槛高。单一数值的临床意义依赖参考区间与个体基线，普通用户看到“空腹血糖 7.4 mmol/L”时，既不知道它意味着什么，也无法判断是否需要干预。其三，异常发现滞后。传统方式依赖定期体检，两次体检之间的指标波动完全处于监测盲区，而高血压、糖代谢异常等慢性病在早期往往只表现为轻微而持续的偏离。其四，缺乏可持续的干预闭环。即使发现了异常，用户也很难获得针对自身数据的可执行建议，健康管理难以长期坚持。
[136][s35] 针对上述问题，本课题设计并实现基于多源健康数据融合的智能监测与预警系统（HHS）。平台以“统一采集—量化评估—智能预警—个性指导”为主线：通过快捷录入、AI 文本解析、OCR 图片识别、设备自动同步四种方式解决数据入口分散的问题；通过多维度健康评分把零散指标转化为可比较的健康状态；通过可配置的多级阈值与预警合并机制，在指标偏离的第一时间主动提醒；通过接入大语言模型，结合用户自身健康档案给出可执行的解读与建议。平台同时提供预防保健、体检报告管理、实时监控、保健追踪与游戏化激励等模块，使健康管理形成持续闭环。
[137][s35] 从工程价值看，本课题覆盖前后端分离架构、关系型数据库设计、缓存与限流、WebSocket 实时通信、第三方 OAuth 授权、大模型应用集成、容器化部署与持续集成等主流企业级技术要点，能够较为完整地检验软件技术专业所要求的分析、设计、编码、测试与文档能力。因此，开发该平台既具备明确的现实需求，也具备充分的教学训练价值。
[138][s34] 1.2 项目范围
[139][s35] 根据需求分析，本平台面向普通用户与系统管理员两类角色，共划分为十四个功能模块，分别是：注册登录与身份认证模块、健康档案管理模块、健康数据录入模块、健康指标管理模块、健康评分模块、智能预警模块、AI 健康顾问模块、预防保健与体检报告模块、实时监控模块、保健追踪模块、游戏化激励模块、多渠道推送模块、设备接入与数据同步模块、系统配置与日志审计模块。下面分别说明各模块的功能要求。
[140][s4] 1.2.1 注册登录与身份认证模块
[141][s35] 系统采用用户名与密码的登录方式，配合 JWT 无状态令牌实现身份识别，并结合角色识别控制菜单权限与数据权限。因此认证功能是整个平台的安全入口。
[142][s35] （1）用户注册
[143][s35] 未登录用户可在注册页填写用户名、密码、昵称、手机号、邮箱、性别、出生日期、身高、体重与血型等信息。提交时后端校验用户名的唯一性、密码强度与手机号格式；注册成功后系统自动为该用户创建一条健康档案记录，用户无需二次填写。
[144][s35] （2）登录认证
[145][s35] 要求对正确的用户名与密码进行认证放行，对错误的凭据拒绝登录并返回统一提示，不暴露“用户不存在”与“密码错误”的差异，避免账号枚举。认证成功后签发 JWT，前端持久化令牌并在后续请求中通过 Authorization 头携带。
[146][s35] （3）访问控制
[147][s35] 在未登录的情况下，除登录页与注册页外，任何前端路由均跳转至登录页；后端对业务接口统一做令牌校验，令牌失效或过期时返回 401，前端自动清除本地状态并跳回登录页。管理员专属功能（如设备平台配置）额外校验角色。
[148][s4] 1.2.2 健康档案管理模块
[149][s35] 健康档案是全部健康分析与预警计算的个体基线来源，记录用户相对稳定的身体特征与病史信息。
[150][s35] （1）档案查看
[151][s35] 登录后进入个人档案页，展示性别、出生日期、身高、体重、BMI、血型、过敏史、家族病史与生活习惯等信息。BMI 由身高体重自动换算，无需用户填写。
[152][s35] （2）档案编辑
[153][s35] 用户可修改除用户名外的全部档案字段。修改身高或体重后，系统同步重算 BMI，并在下一次健康评分时使用新的基线。
[154][s35] （3）密码修改
[155][s35] 用户需先输入原密码，校验通过后方可设置新密码；新密码不得与原密码相同，且需满足最小长度要求。
[156][s4] 1.2.3 健康数据录入模块
[157][s35] 本模块解决“数据从哪里来”的问题，提供四种互补的录入方式，覆盖不同使用场景。
[158][s35] （1）快捷手动录入
[159][s35] 用户从指标类型下拉框中选择指标，填写数值、单位与记录时间后提交。系统按指标类型做取值范围校验，例如心率需落在合理区间内，超出范围时提示用户确认，避免误录。
[160][s35] （2）AI 文本解析录入
[161][s35] 用户以自然语言描述健康状况，例如“昨天心率 72，血压 120/80，空腹血糖 5.6”。系统调用大语言模型将文本解析为结构化的指标列表，前端以表格形式回显解析结果，由用户核对确认后才写入数据库，避免模型误解析直接污染数据。
[162][s35] （3）OCR 图片识别录入
[163][s35] 用户上传体检报告或化验单图片，系统调用 OCR 服务识别文字，再按模板抽取指标名称、数值、单位与参考范围，生成待确认的指标列表。识别结果同时保留原图与识别日志，便于回溯。
[164][s35] （4）设备自动同步录入
[165][s35] 用户授权绑定华为运动健康或小米健康账号后，系统按定时任务拉取步数、心率、睡眠等数据并批量入库。同指标同时间戳的数据以记录时间为准做冲突消解，避免重复入库。
[166][s4] 1.2.4 健康指标管理模块
[167][s35] 本模块是健康数据的查询与分析中心。
[168][s35] （1）指标列表与筛选
[169][s35] 按记录时间倒序分页展示指标记录，支持按指标类型、起止日期组合筛选。列表展示数值、单位、来源渠道与状态标识，状态由该次记录是否触发预警决定。
[170][s35] （2）趋势分析
[171][s35] 选择某一指标后展示其近 7 日、30 日或自定义区间的变化曲线，并在图上标注参考区间与预警阈值，使用户直观看到指标相对基线的偏离程度。
[172][s35] （3）指标维护
[173][s35] 用户可修改或删除误录的指标记录。删除操作写入删除日志，保留操作人、目标对象、时间与来源 IP，便于审计。
[174][s4] 1.2.5 健康评分模块
[175][s35] 把多维指标压缩为单一可比较的分值，帮助用户快速判断当前健康状态。
[176][s35] （1）评分计算
[177][s35] 评分由健康档案、医学指标、风险评估、筛查报告、保健指标五个因子加权合成，权重分别为 25%、35%、20%、10%、10%。各因子依据指标是否落在参考区间、偏离幅度打分，满分 100 分按各因子失分加权扣减，最终映射到优秀（85 分及以上）、良好（70 至 84）、一般（50 至 69）、较差（50 分以下）四档。系统同时由实时指标推导出心血管、代谢、体重、生活方式四个细项维度分，随每次评分一并入库，供历史趋势追溯。
[178][s35] （2）评分展示
[179][s35] 以仪表盘展示总分与等级，以雷达图展示五个评分因子的相对强弱，并列出各因子的得分与权重，明确指出需要改善的方向。
[180][s35] （3）历史与报告
[181][s35] 保存每次评分的历史记录，展示分值的周度变化趋势。用户可一键生成 AI 健康报告，由大模型结合评分明细与近期指标生成自然语言的综合解读与改善建议。
[182][s4] 1.2.6 智能预警模块
[183][s35] 区别于简单的阈值判断，本模块构建了一套完整的预警子系统，是平台的核心价值点。
[184][s35] （1）多级阈值判定
[185][s35] 每个指标可配置警告与严重两级的高、低阈值。指标录入后立即与阈值比对，命中则生成对应级别的预警；未配置个性化阈值的指标使用系统默认阈值。
[186][s35] （2）个性化阈值配置
[187][s35] 用户可按自身情况调整各指标的阈值。例如高血压患者的收缩压阈值可下调至130 mmHg，使预警更贴合个体风险。
[188][s35] （3）预警合并去重
[189][s35] 同一指标在时间窗内反复越界时，系统将相似预警合并为一条并累计触发次数，避免短时间内大量重复告警造成“告警疲劳”。合并过程写入合并日志以便追溯。
[190][s35] （4）预警处置
[191][s35] 预警列表支持按级别与状态筛选，用户可标记已读、确认处置或全部标记已读。对未处置的预警，页面以未读计数提醒。
[192][s35] （5）恢复通知
[193][s35] 当指标重新回到正常区间时，系统主动推送恢复通知，让用户确认干预已生效。
[194][s35] （6）多渠道推送
[195][s35] 预警除通过 WebSocket 实时推送到前端外，还可按用户配置通过邮件、飞书或企业微信送达，确保重要预警不被遗漏。
[196][s4] 1.2.7 AI 健康顾问模块
[197][s35] 为用户提供基于自身数据的健康咨询服务，而非通用问答。
[198][s35] （1）对话咨询
[199][s35] 用户以自然语言提问，系统将用户健康档案、近期指标与评分摘要作为上下文一并提交给大模型，使回答带有个人针对性。回复以 Markdown 渲染，并做 XSS 过滤。
[200][s35] （2）会话管理
[201][s35] 按会话组织历史消息，支持查看历史会话列表、继续既有会话与删除会话。
[202][s35] （3）用量控制
[203][s35] 对 AI 接口按用户做频率与次数限制，超出配额时提示剩余次数，防止接口被滥用。
[204][s35] （4）浮动助手
[205][s35] 除独立的 AI 顾问页面外，在其余页面右下角提供可拖拽的浮动入口，点击展开轻量对话面板，降低咨询路径长度。
[206][s35] （5）免责声明
[207][s35] 所有 AI 输出均标注“仅供参考，不构成医疗诊断”，明确系统定位。
[208][s4] 1.2.8 预防保健与体检报告模块
[209][s35] （1）风险评估
[210][s35] 结合健康档案中的年龄、性别、BMI、家族病史与近期指标，评估 2 型糖尿病、高血压、冠心病、慢性肾病等常见疾病的相对风险等级，并给出对应的干预建议。
[211][s35] （2）体检报告管理
[212][s35] 支持上传体检报告并归档，按体检日期与机构检索。每份报告抽取化验指标并标注异常项，异常项与参考范围并列展示，便于用户快速定位问题。
[213][s35] （3）报告对比
[214][s35] 选择两次体检报告进行对比，逐项展示指标变化方向与幅度，帮助用户判断某项异常是在改善还是在恶化。
[215][s4] 1.2.9 实时监控模块
[216][s35] 面向佩戴设备时的连续监测场景。
[217][s35] （1）实时数据接入
[218][s35] 通过 WebSocket 建立长连接，设备或模拟数据源按秒推送指标，服务端转发至订阅该用户的客户端。
[219][s35] （2）实时展示
[220][s35] 页面顶部展示心率、血氧、体温、步数等关键指标的最新值，下方以滚动曲线展示最近 60 秒的变化，并同步展示推送事件流。
[221][s35] （3）连接状态管理
[222][s35] 前端展示连接状态，断线后自动重连并提示用户，避免用户误以为数据仍在更新。
[223][s4] 1.2.10 保健追踪模块
[224][s35] （1）心情与作息记录
[225][s35] 用户每日记录心情、精力、压力与睡眠质量，形成情绪与作息的长期曲线。
[226][s35] （2）健康目标
[227][s35] 用户设定目标类型、目标值与截止日期，系统按录入数据自动计算完成进度，并在接近截止时提醒。
[228][s35] （3）健康提醒
[229][s35] 支持按固定周期或 Cron 表达式设置提醒，例如“每天 8:00 提醒测量血压”，到期通过配置的渠道推送。
[230][s4] 1.2.11 游戏化激励模块
[231][s35] 通过正反馈提升用户长期坚持的意愿。
[232][s35] （1）积分体系
[233][s35] 录入指标、完成目标、连续打卡等行为触发积分入账，积分流水可查。
[234][s35] （2）成就系统
[235][s35] 设置若干成就条件，达成后自动解锁并在页面提示。
[236][s35] （3）连续打卡
[237][s35] 统计用户连续记录健康数据的天数，中断后重新计数，形成轻量的坚持激励。
[238][s4] 1.2.12 多渠道推送模块
[239][s35] （1）推送渠道配置
[240][s35] 用户可按预警级别分别配置 WebSocket、邮件、飞书、企业微信四个渠道的开关，实现“严重级全渠道、警告级仅站内”这类差异化策略。
[241][s35] （2）推送记录
[242][s35] 每次推送都记录渠道、目标、结果与时间，推送失败时记录失败原因，便于排查。
[243][s4] 1.2.13 设备接入与数据同步模块
[244][s35] （1）平台授权绑定
[245][s35] 用户点击连接后跳转至华为或小米的 OAuth 授权页，授权回跳后系统以授权码换取访问令牌，加密后存储。回调时校验 state 参数，防止授权码被劫持重放。
[246][s35] （2）手动与定时同步
[247][s35] 用户可手动触发同步，系统亦按计划任务定时同步。每次同步记录拉取条数、成功条数与状态，形成同步历史。
[248][s35] （3）同步限流
[249][s35] 对同步接口做频率限制，避免频繁调用触发第三方平台的风控。
[250][s4] 1.2.14 系统配置与日志审计模块
[251][s35] （1）设备平台配置
[252][s35] 管理员维护各设备平台的 OAuth 应用密钥、回调地址与启用状态，配置变更即时生效，普通用户不可见。
[253][s35] （2）操作审计
[254][s35] 记录删除等敏感操作，包含操作人、目标类型、目标标识、时间与来源 IP。
[255][s35] （3）数据导出
[256][s35] 支持将个人健康指标导出为 CSV、Excel 或 JSON，导出任务异步执行，完成后可下载结果文件。

[397][s2] 2  设计思路与技术方案
[398][s35] 经过分析与调研，本系统由十四个功能模块组成，他们分别是注册登录与身份认证、健康档案管理、健康数据录入、健康指标管理、健康评分、智能预警、AI 健康顾问、预防保健与体检报告、实时监控、保健追踪、游戏化激励、多渠道推送、设备接入与数据同步以及系统配置与日志审计。本期主要完成：健康档案管理、健康数据录入、健康指标管理、健康评分、智能预警、AI 健康顾问与设备接入同步。就相关模块的设计思路与技术方案分析如下。
[399][s34] 2.1 系统核心业务流程图
[400][s35] 平台的核心业务链路围绕“一条指标记录如何变成一次有效干预”展开，如图 2.1 所示。用户完成认证后，可选择四种方式之一录入数据；数据经过字段校验与时间戳去重后写入指标表，并发布一条领域事件。事件被异步监听，分别驱动预警评估、健康评分刷新与积分发放三条支线，最终汇聚到前端可视化展示。采用异步事件而非同步调用，使录入请求不必等待告警与评分计算完成，既缩短了响应时间，也避免了任一分析环节故障拖垮主流程。

[709][s34] 2.4 技术方案
[710][s35] 本系统采用前后端分离架构，前端与后端通过 RESTful 接口交互，实时数据通过 WebSocket 传输。前端使用 Vue 3 + TypeScript + Vite 构建，配合 Element Plus 组件库、Pinia 状态管理与 ECharts 数据可视化；后端使用 Java 17 + Spring Boot 3.2，持久层采用 MyBatis-Plus，认证采用 Spring Security 6 与 JWT。数据库选用 MySQL 8.0，缓存与限流使用 Redis 7.0。AI 能力通过 LangChain4j 接入阿里云通义千问，图片文字识别接入百度 OCR，设备数据通过华为运动健康与小米健康的 OAuth 2.0 接口获取。部署方面采用 Docker 多阶段构建与 Docker Compose 编排，由 Nginx 统一提供静态资源与反向代理，并通过 GitHub Actions 完成持续集成与发布。
[711][s35] 开发过程中，使用 Google Checkstyle 对后端代码做规范审计，前端使用 ESLint 与 Prettier 统一格式；数据库表名、字段名与包名均遵守统一命名规范，详见 2.4.2 至 2.4.5 节。系统整体架构如图 2.4 所示，自上而下分为用户层、接入层、前端层、后端层、数据层与外部服务六层，各层职责单一、依赖单向，便于独立演进。

[715][s4] 2.4.2 数据库命名规则
[716][s35] 表达是与否概念的字段，必须使用 is_xxx 的方式命名，数据类型使用 unsigned tinyint（1 表示是，0 表示否）。说明：任何字段如果为非负数，必须是 unsigned。
[717][s35] 正例：表达逻辑删除的字段名 is_deleted，1 表示删除，0 表示未删除。
[718][s35] 表名、字段名必须使用小写字母或数字，禁止出现数字开头，禁止两个下划线中间只出现数字。数据库名、表名、字段名均不使用保留字。
[719][s35] 正例：sys_user、health_metric、alert_rule、user_threshold
[720][s35] 反例：SysUser、healthMetric、level_3_name
[721][s35] 表名不使用复数名词。说明：表名应该仅仅表示表里面的实体内容，不应该表示实体数量，对应于实体类名也是单数形式，符合表达习惯。
[722][s35] 主键统一命名为 id，外键统一采用“关联表单数名_id”，例如 user_id、profile_id。时间字段统一使用 created_at / updated_at 或 create_time / update_time，同一张表内不混用两种风格。
[723][s4] 2.4.3 类命名规则
[724][s35] 类名使用 UpperCamelCase 风格，必须遵从驼峰形式，但以下情形例外：DO / BO / DTO / VO / AO。
[725][s35] 正例：HealthMetricController / HealthMetricServiceImpl / AlertRuleEngine / MetricRecordedEvent
[726][s35] 反例：healthMetricController / HealthMetricControllerImpl / alert_rule_engine
[727][s35] 接口实现类统一使用“接口名 + Impl”命名；领域事件统一以 Event 结尾；事件监听器统一以 Listener 结尾；枚举类型统一放在 enums 包并以 Enum 结尾。
[728][s4] 2.4.4 方法、参数、成员变量、局部变量命名规则
[729][s35] 方法名、参数名、成员变量、局部变量都统一使用 lowerCamelCase 风格，必须遵从驼峰形式。
[730][s35] 正例：localValue / getHttpMessage() / inputUserId / isDuplicate() / resolveConflict()
[731][s35] 常量命名全部大写，单词间用下划线隔开，力求语义表达完整清楚，不要嫌名字长。正例：MAX_FILE_SIZE / ALERT_MERGE_WINDOW_MINUTES。

[749][s2] 3  设计内容（过程）与说明
[750][s35] HHS 智能健康监测平台设计完成后，交付内容主要有数据库设计、界面原型设计、类设计、顺序图设计、API 接口设计与测试文档。本系统涉及的功能点共计 60 余个，数据库表共计 35 张，后端控制器 25 个、业务服务接口 37 个，前端路由页面 22 个，各类型界面原型 11 个。以下分别说明。
[751][s34] 3.1 数据库设计
[752][s35] 数据库设计是系统设计的基础。本项目数据库名为 hhs，字符集采用 utf8mb4，排序规则为 utf8mb4_unicode_ci，共包含 35 张数据表，按职责可划分为五组：用户与档案组（sys_user、health_profile、delete_log）、指标与实时数据组（health_metric、realtime_metric、health_score_history、health_score_cache）、预警组（health_alert、alert_rule、user_threshold、alert_template、alert_merge_log、push_history、user_push_config）、预防与报告组（examination_report、lab_result、ocr_health_record、ocr_recognize_log、risk_assessment、health_report、screening_record、ai_conversation、ai_parse_history）、设备与保健组（device_connection、sync_history、device_platform_config、user_reminders、user_streaks、achievements、user_achievements、user_points、health_goals、goal_progress、mood_entries、export_jobs）。表与表之间的关系以及各表具体设计如下。
[753][s4] 3.1.1 数据库物理模型
[754][s35] 数据库物理模型如图 3.1 所示。全部业务表均以 user_id 关联用户表，形成以用户为中心的一对多结构；实时指标表按月份做 Range 分区，以支撑高频写入；用户阈值表与预警表通过 metric_key 形成逻辑关联，使同一指标的历史阈值变更可追溯。

[1269][s34] 3.2 界面设计
[1270][s35] 本系统由用户端与管理端两部分组成，其中用户端页面共计 15 张，管理端页面共计 7 张，合计 22 个路由页面。页面统一采用侧边栏导航、顶部栏与内容区三段式布局。为突出页面结构与信息层级，以下界面设计图采用灰度线框原型表达，仅保留布局、控件与数据区域，具体配色与视觉样式以系统实际界面为准。以下按页面分组说明设计思路，并给出主要页面的原型图。
[1271][s4] 3.2.1 用户登录页面
[1272][s35] 用户在浏览器输入网址后，系统将跳转到登录页。页面居中呈现品牌标识、系统名称与登录表单，表单包含用户名、密码两个输入框及密码可见性切换按钮；表单下方提供“立即注册”链接与实时监控、AI 顾问、健康评分三个功能快捷入口。用户名或密码为空时，提交按钮会就地提示，避免无效请求。如图 3.2 所示。

[1275][s4] 3.2.2 用户注册页面
[1276][s35] 用户在登录页点击“立即注册”进入注册页。页面采用居中卡片布局，自上而下依次为品牌标识、页面标题与副标题、用户名、密码、确认密码、邮箱（可选）四个输入项，以及“立即注册”按钮。表单下方提供“已有账户？立即登录”链接，并以数据安全、健康追踪、AI 顾问三项能力说明帮助用户建立信任。提交后系统自动创建账户与健康档案，用户无需二次录入。如图 3.3 所示。

[1348][s34] 3.5 API接口设计
[1349][s35] 为保证前后端能够独立开发与并行推进，系统对外接口遵循统一的约定：所有接口以 /api 为前缀；请求与响应统一使用 JSON；响应体统一封装为 Result<T>，其中 code 为 200 表示成功，非 200 表示业务异常并携带 message；认证接口外的全部接口需在请求头携带 Authorization: Bearer <token>；分页接口统一使用 page 与 size 两个查询参数，返回 Page<T> 结构。通过定义清晰的接口，可以实现系统之间的解耦合，提高系统的灵活性和可扩展性，同时也便于前端与第三方系统按统一方式接入。以下给出四个核心接口的详细设计。

[2002][s34] 4.1 部署手册
[2003][s35] 本系统提供两种部署方式：一是使用 Docker Compose 一键启动全部服务，适合演示与答辩现场；二是分别启动数据库、后端与前端，适合开发调试。以下以 Docker 方式说明部署步骤，环境要求为 Docker 20.10 及以上，服务器内存不低于 2 GB。
[2004][s4] 4.1.1 准备环境与配置
[2005][s35] 在部署机器上安装 Docker 与 Docker Compose，执行 docker --version 与 docker compose version 确认安装成功。
[2006][s35] 获取项目源码，进入项目根目录。
[2007][s35] 复制环境变量模板：cp .env.example .env。
[2008][s35] 编辑 .env，至少填写数据库密码 DB_PASSWORD、Redis 密码 REDIS_PASSWORD 与 JWT 密钥 JWT_SECRET（不少于 32 字符，可用 openssl rand -base64 32 生成）。如需启用 AI 与 OCR 功能，另需填写 DASH_SCOPE_API_KEY 与百度 OCR 的 API_KEY、SECRET_KEY；如需启用设备同步，填写对应平台的 OAuth 凭据。
[2009][s4] 4.1.2 附加数据库
[2010][s35] 数据库无需手工创建：后端容器首次启动时会自动执行 src/main/resources/sql/schema.sql 完成建表。
[2011][s35] 如需手工初始化，可先执行 docker compose up -d mysql，然后使用 docker exec 进入容器执行 mysql -u root -p hhs < schema.sql。
[2012][s35] 执行完毕后可用 SHOW TABLES 确认 35 张业务表已全部创建。
[2013][s4] 4.1.3 启动应用
[2014][s35] 执行 docker compose up -d 启动前端、后端、MySQL 与 Redis 四个服务。
[2015][s35] 执行 docker compose ps 查看容器状态，确认四个服务均为 running。
[2016][s35] 执行 docker compose logs -f backend 查看后端启动日志，出现 Started HhsApplication 即表示启动成功。
[2017][s4] 4.1.4 访问系统
[2018][s35] 在与服务器网络互通的客户机上打开浏览器。
[2019][s35] 在地址栏输入 http://服务器IP 或已配置的域名，页面跳转到登录页。
[2020][s35] 使用注册的账号登录，或点击“立即注册”创建新账号，注册完成后即可访问各功能模块。
[2021][s35] 后端接口文档默认可通过 http://服务器IP:8082/doc.html 访问。
