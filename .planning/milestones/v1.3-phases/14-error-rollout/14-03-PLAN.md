<objective>
Decide the whole vocabulary once, before any of the thirteen forms starts migrating, and remove the last two obstacles that would make each migration a copy-paste job. This plan supplies the labels and the shared collector that ERR-03's inline binding requires.

Two distinct problems are solved here. First, the rollout is about to add roughly ninety `showError` calls across thirteen forms, each needing a fallback key; if the key set is decided per-wave, `errorMessages.spec.ts` gets edited in every wave and the "only extend the array" discipline erodes by the third batch. Research's recommendation is explicit: fix the final key set before the first migration wave. Second, `collectInvalidFieldMessages` already exists verbatim in two files and is needed by thirteen more; extracting it now costs one task, and extracting it later costs a thirteen-file cleanup with guaranteed drift.

The field-label question has a concrete user-visible failure attached. `FIELD_LABELS` at 17 keys covers the threshold and profile forms only. A mood submission is validated by `@NotNull` constraints on `moodScore`, `energyLevel`, `stressLevel` and `sleepQuality`, so a 400 is reachable and the summary would render `moodScore：不能为空` — a raw camelCase key in the user's error list. Contract 4.5 rule 2 says an unknown field renders the backend message alone, which is a defensible fallback for most fields but not for a form whose four required fields are all unknown. That is why this plan takes the contract's 22 plus the 5 mood keys.

Purpose: every later migration task should be one mechanical edit, not a vocabulary decision plus a helper extraction plus a spec edit.

Output: a 46-key dictionary, a 44-entry label table with the count assertion raised deliberately rather than broken accidentally, a `labels` override on the composable, and one shared `collectInvalidFieldMessages` consumed by both existing reference implementations.
</objective>
