<objective>
Execute D-02: a Pinia store is not a UI layer, so it must not raise toasts. Resolve all eight store-internal error calls by moving the presentation decision to the caller. The wellness callers adopt D-03's state-block channel for their load paths.

The per-method decision is not uniform, and the shape of each method's existing return contract is what decides it. Four loaders return `void`: throwing costs nothing and fixes a real defect, because two of them currently swallow a failure into a plausible-looking empty value. `getHistory` returns `[]` on failure today, which makes "the history request failed" indistinguishable from "this conversation has no history" — the dialog renders empty either way. `fetchSummary` leaves the dashboard showing whatever it had, which reads as a real zero. Throwing is what lets the caller say which of the two happened.

Three methods return a boolean that both callers already branch on. Converting those to throw would force every caller to change for no user-visible gain, so the boolean stays and only the toast is removed. `deleteSession` is the subtle one: it returns a boolean but its only caller wraps the whole confirm-and-delete in a bare catch commented "User cancelled", so a real failure is currently reported as a cancellation. That caller needs the split, and once it is split the store can throw — but keeping the boolean is also viable. This plan chooses throw for the delete specifically because the split caller has to be rewritten anyway, and because a swallowed delete failure with the session still in the list is an inconsistency the user can see.

The send-message path needs a different treatment entirely. Today the store pops the optimistic message and returns `false`; the UI removes the bubble and says nothing. Migrating that to a toast would be a behaviour change that makes a disappearing chat message produce a transient banner — worse than the current nothing, because the user's text is gone. The right surface is in place: restore the text to the composer and show the user that the send did not complete. The research resolved this explicitly and forbade adding a dictionary key for it, so no `ai.sendFailed` exists and none may be added.

Purpose: remove the last eight bare error calls and convert two silent-swallow defects into distinguishable states, without touching the three legitimate success toasts that Contract 5 §5.1 permits.

Output: three stores with no presentation, six callers that now own it, two specs pinning both the contract and the send-failure experience.

<invariant>
`stores/push.ts` is already the correct shape — it calls `showError(..., { silent: true })` to classify without presenting and stores the message for the view to render. Do not refactor it. It is referenced here only as the pattern the other stores now follow, and `ErrorLayerSample.spec.ts` already asserts it contains no error toast.
</invariant>
</objective>
