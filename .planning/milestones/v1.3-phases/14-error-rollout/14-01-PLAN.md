<objective>
Land the three A-1 foundation changes that every later plan consumes, and prove the state-block channel works end-to-end on the one surface where a 403 is unconditionally reachable. This plan implements D-03's page-level-403 rule and its zero-toast requirement.

This plan carries the phase's single most load-bearing change: the two new `ErrorKind`s. Today `normalizeApiError` has no branch that can produce a 403 or 404 kind, so a real HTTP 403 falls past the 5xx check and lands on the final fallback as `server` with `retryable` unset — which `showError` renders as a *sticky, retryable server toast* inviting the user to retry a permission denial. Envelope 403/404 do worse: they land on the envelope branch as `business`, a plain toast. Both destroy the channel separation that ERR-07 requires.

The insertion point is a contract, not a detail: the new branches go after the 401 guard (line 110) and before the no-response guard (line 116). Before 401 and a session expiry would be misclassified as a permission failure; after no-response and they could never fire, because every `ApiError` short-circuits at step 0 and every non-ApiError without a `response` is already handled.

Purpose: without this, 87 migrations get written against a classification that cannot express what they are migrating to, and every 403/404 surface becomes dead code or a retryable toast. D-03's "403 全页级、404 内容区级，均不弹 toast" is unimplementable until `presentStates` exists with a zero-toast default.

Output: `ErrorKind` with 9 members, `showError` with `presentStates`, `ErrorState` with `scope`/`actions`, the S1 page block on `DevicePlatformConfig`, and the tests that pin all of it — including A-2's four anti-regression cases, which are the only thing standing between this phase and a silently re-inverted classification order.
</objective>
