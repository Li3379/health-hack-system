<objective>
Close the last three server-validated forms that the rollout's inventory accounts for but this plan set had not yet wired: both auth forms and the push settings page.

This plan exists because of a source-audit check, not a scheduling preference. The inventory's thirteen remaining forms include `auth/Login.vue` (item 11), `auth/Register.vue` (item 12) and `user/PushSettings.vue` (item 13), and the backend confirms all three are `@Valid`-validated: `LoginRequest` has `@NotBlank` on both fields, `RegisterRequest` has `@NotBlank`+`@Size` on username and password plus `@Email` on email, and `PushConfigRequest` has `@Pattern` on the channel type and `@Size(max = 500)` on the config value. A 400 with `fieldErrors` is therefore reachable on all three — which means leaving them unwired would leave ERR-03 short of its "全站所有表单提交" wording.

The research marked the push DTO as having no constraints and therefore out of scope. That finding does not hold: `PushConfigController.java:102` applies `@Valid` and `PushConfigRequest` declares both constraints. The consequence is that an over-long paste into a webhook URL currently produces a toast naming a field the user cannot see labelled, and the field itself is not marked. That is exactly the condition ERR-03 exists to remove, so the page is in scope rather than exempt.

Both auth forms need one care point: they already call `showError` in their catch, so the migration is not "add showError" but "capture its return value and conditionally project". Their existing client-side rules stay — the server projection supplements them, and removing the rules would turn an obvious empty-field problem into a round trip.

Purpose: no `<el-form>` on the app that submits to a validated endpoint is left without an inline projection.

Output: three converted forms, two specs pinning the auth preserves and the push per-channel isolation, and a ledger fragment closing the last thirteen-form gap.

<scope_note>
`health/Thresholds.vue` is deliberately **not** in this plan. It contains zero `<el-form>` elements, so it has no `prop`/`:error` anchor and its `presentValidation: true` exception stays as the UI-SPEC sanctions. `health/Metrics.vue` and `health/Alerts.vue` are also excluded: their only forms are filter forms issuing GET requests with no server field validation, which plan 14-09 already records.
</scope_note>
</objective>

    **The collision, stated first.** The page renders one `el-form` per channel in a `v-for`, and each binds `{ configValue: … }`. A single composable instance would put channel A's `configValue` error onto channel B's field, because both forms share the key `configValue`. The fix is not one instance per channel inside a template loop (composables cannot be created inside a `v-for` without violating the setup-time rule) — it is **one instance whose error map is keyed by channel**, with the field name namespaced per channel.

    Implement it as one `useFormServerErrors` whose error map is keyed by a per-channel composite rather than the bare field name — the composite is the channel type joined to the field name by a separator, so `configValue` for the email channel and `configValue` for the wecom channel are two distinct entries, and the inline binding for channel N reads only its own composite. Keep the mapping in one small helper in the file so the template's `:error` expression stays a plain lookup and the composable's global label resolution still finds `configValue` for the summary. Because `fieldLabel` will not recognize a composite key, pass a `labels` map that maps each composite back to the channel's own label from `getConfigLabel` — that keeps the summary readable ("企业微信 Webhook：配置内容不能超过 500 个字符") rather than showing a composed key.

    Then: each channel's `el-form` gets `prop="configValue"`, `data-field` set to the composite key, `:error` reading the composite, and a clear-on-change handler on its input. A `FormErrorSummary` is rendered once per channel body, above that channel's form, bound to a computed that filters the shared error map to that channel — filtering is necessary because the summary otherwise lists other channels' errors.

If the store swallows the error and returns only a boolean, the field projection is impossible from the view — in that case the correct change is to have `saveConfig` also assign a `saveError` ref the view can read (mirroring `loadError`), and record that in the ledger.
