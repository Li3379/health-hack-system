<objective>
Create the frontend single source of truth for profile completeness: typed contracts, the API call, an offline catalog, and a Pinia store that owns loading, failure and the 7-day dismissal window.

Purpose: D-01 forbids the frontend from computing completeness, so the store must be a pass-through with an explicit, distinguishable failure state. UI-SPEC Contract 8 requires that a load failure renders nothing while a genuine 404 renders a synthesized 0% — those are different user situations and must never collapse into one. UI-SPEC Contract 1 requires the segment count to come from `fields.length`, which means the store must carry the whole array, not just a number. This plan builds that contract layer before any component exists, so the three components in the next wave can be pure renderers.

Output: `ProfileCompletenessVO` / `ProfileFieldStatusVO` types, `preventionApi.getCompleteness`, `utils/profileFields.ts`, `stores/profileCompleteness.ts`, and the Wave-0 store spec.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend JSON → Pinia store | Response shape is trusted only after type assertion; a missing `fields` array would break every renderer |
| localStorage → store | `hhs_profile_reminder_dismissed_at` is user-writable and may be corrupt or hand-edited |
| store → API | Every page that mounts the banner or header triggers a fetch |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-17 | Tampering | localStorage dismissal | low | mitigate | A corrupt or hand-edited timestamp is treated as "not dismissed", so tampering can only show the reminder more often — never suppress it permanently (fail-open, not fail-silent) |
| T-13-18 | Denial of Service | Concurrent fetches | low | mitigate | The `if (inFlight) return inFlight` single-flight guard is asserted by test (exactly one HTTP call), so a page rendering three consumers issues one request — and because the shared promise is returned rather than dropped, an awaiting caller cannot observe a pre-settlement `data` |
| T-13-19 | Repudiation | Synthesized 0% | medium | mitigate | Synthesis happens only on a real 404; a transport failure leaves `data` null and sets `loadFailed`, and a test asserts the two states are distinguishable |
| T-13-20 | Information Disclosure | Store payload | low | accept | The payload is the caller's own field labels and backend constant copy; the endpoint is user-scoped server-side |
| T-13-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs in this plan; the offline catalog is hand-written from the backend constant, not fetched from a registry |
</threat_model>
