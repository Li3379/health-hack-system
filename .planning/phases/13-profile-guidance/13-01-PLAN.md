<objective>
Create the authoritative backend completeness source: a pure 9-field catalog plus a weighted calculator that returns score / level / filledCount / totalCount / fields[].

Purpose: D-01 locks completeness to the backend and forbids the frontend from computing it. Every later surface (profile page header, dashboard compact row, banner trigger, risk badge, backfill panel) reads the same object, so the weighting, the three level thresholds and the per-field `reason`/`assumption` copy are decided exactly once, here. The existing `ProfileScorer` hard-coded deduction scheme (`-10/-15/-10/-15`, empty profile → 70) cannot serve this: it produces no field list, no level, and its 70-for-empty value would make an empty profile look half-complete.

Output: `ProfileFieldCatalog`, `ProfileCompletenessCalculator`, `ProfileCompletenessVO`, `ProfileFieldStatusVO`, and the two Wave-0 test classes that pin them. No HTTP surface yet (13-02), no score/risk VO changes (13-03/13-04).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| health_profile row → completeness calculation | The row is user-authored; every field can be null, blank or stale, and the calculator must not throw or over-report completeness |
| catalog copy → user-visible UI | `reason` and `assumption` strings cross into the browser verbatim and are the sole explanation users get for why a field matters |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-01 | Tampering | ProfileCompletenessCalculator.isFilled | medium | mitigate | `bmi.filled` requires heightCm AND weightKg AND bmi, so a stale bmi column cannot inflate a user's reported completeness (RESEARCH Pitfall 5) |
| T-13-02 | Information Disclosure | ProfileFieldCatalog reasons | low | mitigate | Reason strings are backend constants with no exception text or SQL; a test rejects the nine raw camelCase field identifiers so no internal property name (heightCm) leaks to the UI |
| T-13-03 | Repudiation | Weighted score | medium | mitigate | Weights sum to exactly 100 and are asserted by test; the level boundary ownership (59/60/84/85) is asserted, so a user cannot be told they are 标准档案 while the system treats them as 基础档案 |
| T-13-04 | Denial of Service | calculate(null) | low | accept | Null profile is a legitimate first-run state; the calculator is null-safe by construction and the null branch is covered by a test, so no explicit guard is needed |
| T-13-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs no packages. If a later task introduces one, a blocking human checkpoint plus a registry legitimacy check is required before install |
</threat_model>
