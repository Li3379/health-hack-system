<objective>
Add the authoritative server-side threshold validation (`@ValidThresholdRange` on `UserThresholdRequest`) and extend the metric metadata registry with `alertable` and a backend-computed recommended threshold, so the frontend wizard can be driven entirely by metadata instead of a hardcoded list.

Purpose: THR-05 requires that a direct API call cannot store an invalid threshold ordering or a physiologically impossible boundary; the UI is only a convenience. THR-01/THR-02 require the picker scope and default values to come from the backend (D-03, D-06) — a frontend whitelist would drift from `alert_rule`.
Output: A class-level constraint that lands two inline-able field errors per violation, and a metadata response carrying `alertable` + `recommended` for all 23 metrics.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → POST/PUT /api/thresholds | Untrusted boundary numbers and metricKey cross here; the class-level constraint is the authoritative gate |
| GET /api/metrics/metadata → browser | Public unauthenticated endpoint; the payload drives which metrics the wizard offers |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-12 | Tampering | ThresholdRangeValidator | high | mitigate | Class-level constraint rejects inverted ordering and hard-limit violations server-side, so a direct API call cannot bypass the UI's `:min/:max` (ASVS V5) |
| T-12-13 | Information Disclosure | Constraint violation messages | medium | mitigate | All messages are static Chinese templates with no interpolation of user-supplied strings; the metric display name and hard bounds come from the registry, never from the request body |
| T-12-14 | Tampering | Dot-joined property path | high | mitigate | Two separate `buildConstraintViolationWithTemplate` calls per violation guarantee dot-free field names, so both inputs receive an inline error instead of an unattributable one (RESEARCH §Pitfall 5) |
| T-12-15 | Denial of Service | Stale cached metadata | medium | mitigate | VERSION_TAG bumped to v1.2-metric-meta so the ETag changes and clients holding a 24h-cached payload revalidate rather than running a wizard with no alertable flags |
| T-12-16 | Spoofing | Public metadata endpoint | low | accept | The metadata is non-sensitive reference data (names, units, limits) already intended for anonymous consumption; no user data is exposed |
| T-12-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs in this plan; any future install requires a blocking human checkpoint plus a registry legitimacy check |
</threat_model>
