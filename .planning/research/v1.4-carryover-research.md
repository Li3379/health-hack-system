## 第 1 项：`RiskScorer` 读归因快照

### 现状

```java
// RiskScorer.calculate(Long userId)
RiskAssessment risk = risks.get(0);          // 只取最新一条
return switch (risk.getRiskLevel()) {
    case "LOW" -> 100;
    case "MEDIUM" -> 70;
    case "HIGH" -> 40;
    default -> 70;
};
```

`ScoreCalculator` 用它算健康总分的 20% 权重：

```java
int riskScore = riskScorer.calculate(userId);
totalScore -= (int) ((100 - riskScore) * 0.20);
```

### 关键发现：这是往返丢信息，不是「两套口径」

`riskLevel` **本身就是从 `riskScore` 派生的**：

```java
// RiskAssessmentServiceImpl.create()
if (score >= 60)      r.setRiskLevel("HIGH");
else if (score >= 35) r.setRiskLevel("MEDIUM");
else                  r.setRiskLevel("LOW");
```

所以数据流是：

```
0-100 连续分 ──(>=60/>=35)──> 三档 level ──(100/70/40)──> 三档分值
     ↑                                                        ↓
  真实信息                                          健康总分扣分
```

**范围坍缩实例：**

| 真实 riskScore | level | `RiskScorer` 返回 |
|---|---|---|
| 5 | LOW | 100 |
| 34 | LOW | 100 |
| 35 | MEDIUM | 70 |
| 59 | MEDIUM | 70 |
| 60 | HIGH | 40 |
| 100 | HIGH | 40 |

`riskScore=5` 与 `riskScore=34` 对健康总分的影响**完全相同**；`riskScore=60` 与 `100` 也完全相同。

### 快照能提供什么

`contributors` 快照（`RiskAssessmentVO.contributors`）每个条目含：

- `state` — `CONTRIBUTED` / `NORMAL` / `ASSUMED` / `MISSING`
- `points` — 该项为疾病分数贡献了多少分
- `explanation` — 一句中文说明

`RiskAssessmentVO` 的注释明确写着 `points` **之和等于 `riskScore`**。

所以快照不只记录分数，还记录了**分数由什么构成**。

### 三个可选方案（未选定，供 discuss 阶段决策）

| 方案 | 做法 | 影响 |
|---|---|---|
| **A. 直接用 `riskScore`** | `calculate` 返回 `100 - riskScore` 或类似线性映射 | 最小改动，消除往返损失。但仍是「总分」视角 |
| **B. 读 `contributors` 加权** | 按 `state` 区分 `CONTRIBUTED`/`MISSING`，缺数据的项不计惩罚 | 最诚实：没测的指标不该算「正常」。但会**改变现有用户分数** |
| **C. 不改** | 保持三档映射 | 现状 |

**为什么这不是机械清理：** B 会让「有 4 项血脂没测」的用户分数发生变化——现在按 `riskLevel` 拿固定分，改后按实测项加权。这是产品语义决策，必须显式确认。

### 待确认的问题

1. 健康总分里「风险评估」这 20% 应该反映**疾病严重度**还是**评估可信度**？
2. `MISSING` 的指标在扣分时算 0 还是按人群均值代入？现在 `RiskAssessmentServiceImpl` 用的是「不代入、标 MISSING」，但 `RiskScorer` 这一层看不到这个区分。
3. 改动会让多少现有用户的健康总分变化？需要先跑一次分布统计（未做）。

## 第 3 项：`toVO` 重复

### 现状确认

`HealthMetricServiceImpl:236` 与 `WellnessServiceImpl:330` 的 `toVO` 逐字相同，各 12 行，都是 `HealthMetric → HealthMetricVO` 的投影。

### 上轮 discard 的理由仍然成立

`HealthMetricServiceImpl` **仍在使用显式 `@Autowired` 构造器**（`:51-58`），这是上次失败的根因：

- 加一个构造器参数会漏赋值（编译期能抓）
- 三个测试文件要改（`@Mock` 让 `toVO` 返回 null，而 `@InjectMocks` 在字段初始化后才注入）

代价没变：**一个生产构造器签名 + 三个测试文件，换 12 行重复。**

### 回访条件（上轮已记入 `.auto/prompt.md`）

- 若因其他原因引入 VO mapper，`toVO` 顺便并入
- 若 `HealthMetricServiceImpl` 改用 `@RequiredArgsConstructor`，参数陷阱消失
- 若 `HealthMetricVO` 增加字段，重复从装饰性问题变成真隐患

**结论：维持 discard。**

## 补充：真实数据分布（研究后追加）

原报告的「未做」第一条已补齐。查的是本地开发库（2 个用户、57 条评估）。

### 现状分布

| 疾病 | level | 条数 | riskScore 范围 | 当前 `RiskScorer` | 若用 `100 - score` | 差 |
|---|---|---|---|---|---|---|
| 心血管疾病 | LOW | 16 | 5–12 | 100 | 88.4 | **−11.6** |
| 心血管疾病 | MEDIUM | 3 | 44 | 70 | 56.0 | **−14.0** |
| 糖尿病 | LOW | 16 | 20 | 100 | 80.0 | **−20.0** |
| 糖尿病 | MEDIUM | 3 | 50 | 70 | 50.0 | **−20.0** |
| 高血压 | LOW | 16 | 5 | 100 | 95.0 | **−5.0** |
| 高血压 | MEDIUM | 3 | 40 | 70 | 60.0 | **−10.0** |

### 对健康总分的影响

`ScoreCalculator` 里风险维度权重 20%，扣分是 `(100 - riskScore) * 0.20`：

| 场景 | 健康总分变化 |
|---|---|
| 心血管疾病 LOW | **+2.3** |
| 心血管疾病 MEDIUM | **+2.8** |
| 糖尿病 LOW | **+4.0** |
| 糖尿病 MEDIUM | **+4.0** |
| 高血压 LOW | **+1.0** |
| 高血压 MEDIUM | **+2.0** |

**方向一致：所有用户的健康总分都会上涨。** 因为当前三档映射对低风险用户过度惩罚——`riskScore=5` 的糖尿病和 `riskScore=34` 拿同样的 100 分，而 `100-5=95` 才是真实反映。

这不是「调整口味」，是**修正一个系统性低估**。但用户会看到自己的健康分数上升，需要产品确认这个变化是否可接受（尤其如果已有用户把分数当基准）。

### 快照覆盖率

```
有 contributors 快照: 51 / 57 (89%)
无快照（legacy）:      6 / 57
```

**方案 B 必须处理降级路径**：6 条 legacy 行没有 `contributors`，无法按归因加权。可选：回落到 `100 - riskScore`（方案 A），或回落到当前三档映射。前者一致，后者会造成同一用户不同疾病评分口径分裂。

### 注意样本量

**只有 2 个用户、57 条记录**，且 MEDIUM 每病仅 3 条。这是开发库，不是生产分布。真实影响幅度需要生产数据才能定，但**方向（分数上涨）不受样本量影响**——因为这是映射函数的性质，不是数据性质。

## 补充：方案 B 的代码可行性（研究后追加）

原报告「未做」第二条已补齐。结论：**可行，但有一处真实的架构障碍**。

### 序列化路径（完整）

```
createAssessment()
  └─ serializeContributors(List<RiskContributorVO>) -> JSON string
       └─ row.setContributors(json)            // 写入 risk_assessment.contributors

listByUserId() / getLatest
  └─ deserializeContributors(String json) -> List<RiskContributorVO>
       └─ toVO(..., contributors)              // 读时返回给前端
```

`deserializeContributors` 处理了三种情况：`null`/空串 → 空列表；解析失败 → 空列表并 warn；成功 → 列表。所以降级路径**已有现成实现**，不需要新写。

### 障碍：`RiskScorer` 拿不到这个方法

| | `RiskAssessmentServiceImpl` | `RiskScorer` |
|---|---|---|
| 类型 | `@Service`，实现 `RiskAssessmentService` | 独立 `@Component` |
| 依赖 | `RiskAssessmentMapper` + 多个 | **仅** `RiskAssessmentMapper` |
| 有 `deserializeContributors` | ✅ 但 **private** | ❌ |

`RiskScorer` 目前直接 `selectList` 查库、只读 `riskLevel` 字段，**完全不碰 `contributors` 列**。

三条可行路径：

| 路径 | 做法 | 代价 |
|---|---|---|
| **B1. 注入 service** | `RiskScorer` 依赖 `RiskAssessmentService.listByUserId()` | 引入 domain → service 的反向依赖；`listByUserId` 返回全部历史，需自己取最新 |
| **B2. 下沉 mapper 查询** | `RiskScorer` 自己读 `contributors` 列 + 复制解析逻辑 | 解析逻辑出现第二份（正是 v1.4 刚清掉的那类重复） |
| **B3. 抽公共解析器** | 把 `deserializeContributors` 提到 `RiskContributorCodec` 之类的共享组件，两处都用 | 新增一个类，但**消除了复制**；改动面最小且方向正确 |

**B3 是唯一不制造新重复的方案**，且与 v1.4 Phase 17 的教训一致（`ThresholdComparator` 就是因为「解析逻辑写第二份」而成为缺陷温床）。

### 对方案 A 的补充

如果最终选 A（直接用 `100 - riskScore`），`RiskScorer` **完全不需要改依赖**——它已经查到了 `RiskAssessment` 实体，`getRiskScore()` 就在上面。改动是一行：

```java
// 现在
return switch (risk.getRiskLevel()) { ... };
// 方案 A
return 100 - risk.getRiskScore();
```

**这是 A 与 B 的关键成本差**：A 一行、无架构改动；B 需要 B3 那次抽取 + 降级路径设计。

### 修正后的建议

| 方案 | 改动量 | 分数影响 | 风险 |
|---|---|---|---|
| **A. 线性映射** | 1 行 | 同上表（+1~+4 分） | 极低 |
| **B. 归因加权（B3）** | 新组件 + 两处接线 + 降级 | 同上表（若 MISSING 不计惩罚，可能再高一些） | 中 |
| **C. 不改** | 0 | 无 | 无 |

**A 和 B 消除的是同一个往返损失**（三档坍缩）。B 额外做的「区分 MISSING」是另一件事——它改变的是「没测的指标该不该算正常」，与本次缺陷无关。

**建议先做 A**：一行修掉可证明的缺陷，把 B 的 MISSING 语义作为独立议题另行讨论。否则两件事混在一个改动里，无法判断分数变化是哪一部分造成的。
